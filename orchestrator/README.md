# Local Orchestrator (Admin Agent Runtime, Automaton)

Standalone local server that coordinates orchestration by agents for the
AutoTrading Ideal Platform. It runs the **admin agent** as a standalone
n8n-inspired workflow engine **and automaton**: routes tasks to eagents, tracks
runs, automaton states/transitions, and reports, and executes actions with local
capabilities (shell/files) scoped to the platform.

- No dependency on OpenMausBot or any external bot framework.
- Registry-driven: loads `agents/registry.json` and dispatches to the eagent of
  the owning subplatform.
- **Automaton model (musashaban port, no secrets copied):** constitution/soul,
  access methods, and paywall-building/settlement/funding methods in
  `../musashaban-port/`. Every agent is an automaton; **every eagent reports to
  admin**; admin reports to operator/audit.
- **Admin authority (fail-closed, 0-funding by default):** admin erects
  paywalls, settles, and funds only from realized/authorized resources/policy
  (settlement/funding rails include Pix-Payment-System African/PIX variants when
  configured). No capital assumed; live only — no paper, demo, testnet, backtest,
  simulation or free-tier stand-ins. No capital movement without verified
  funds/keys/accounts and confirmation; otherwise fail closed.

## Start

From the platform root (`AutoTrading-Ideal-Platform`):

```bat
npm start
```

`npm start` installs the single shared dependency tree first (root `node_modules`
+ root `.venv`) and skips it when a manifest fingerprint is unchanged. Use
`npm start -- --no-open` to skip the browser, `npm run init` to install
explicitly, or `SKIP_INIT=1 npm start` to bypass the check. The server itself is
still Python:

```bat
python -m orchestrator
```

Or double-click/run `start-orchestrator.bat` in the platform root.

### Boot activation

At startup admin surveys every component and then **turns the preset directives
into real runs** — boot is not a survey that leaves directives as inert text:

- `blocked`/`needs_setup` components are sent a real `initialize` run, which
  executes `scripts/init-platform.js --component <name>` against that component.
- `ready` components receive a manifest-derived command (build/test/check/lint,
  otherwise a real import or compile check) run in the manifest's own directory.
- Every activation is a durable run with live output and automaton transitions;
  an install is only reported complete when the component re-checks as ready.
- No simulated success: a missing manifest, a failed command or an unavailable
  rail is reported as skipped/blocked with the actual evidence.

`GET /activation` shows the last boot's activation report; `POST /activate`
re-issues it on demand (`{"targets": [...], "auto_init": true|false}`).

Environment (optional):
- `ORCHESTRATOR_HOST` (default `127.0.0.1`)
- `ORCHESTRATOR_PORT` (default `8765`)
- `SKIP_INIT=1` (skip the auto-install check in `npm start`)
- `.env` values (generated by init) are loaded into child processes, e.g.
  `JEV_OFFLINE=1` to run `grok-jev-router` on its free local evaluator.

- `GET /runs` — recent orchestration runs

- `GET /runs/{id}/reports` — reports for a specific run
- `GET /components` — per-subplatform readiness (toolchains, dependencies, manifests, submodules, duplicate copies)
- `GET /components/{name}` — readiness for one subplatform
- `GET /bootup` — last boot survey and automation scope
- `GET /activation` — activation report from the last boot (directives → real runs)
- `POST /activate` — re-issue boot directives as real runs; `{targets?, auto_init?}`
- `GET /observability` — watchdog status and active alerts
- `GET /alerts` — alerts (`?active=1` for active only)
- `GET /skills` — discovered skills; `GET /skills/{id}` for one skill
- `GET /geo/overview` — map/manifest counts; `GET /geo/places|automata|work-items|routes` for records
- `GET /workflows` — catalogue of 20 agentic workflows, five compartments, anatomy, live readiness, depth contracts and architecture summary
- `GET /workflows/{id|slug}` — one workflow with a run preview (incl. `depth`)
- `GET /admin/compartments` — the five compartments and the replicas assigned to each
- `GET /admin/funding-state` — platform funding state (`unfunded` / `float_funded` / `revenue_funded`, amounts)
- `GET /admin/spend-authorizations` — recorded operator spend authorizations (live tokens consumed by `policy.evaluate`)
- `GET /stack` — the agentic architecture: 6 layers, agent loop, environments (16 subplatforms), protocol layer, semantic layer, data products, governance, engineering layers
- `GET /admin/settlement/status` — RudiPay (port of musashaban payment/settlement) + funding + withdrawal state: routers, faucets, active txs, settlement totals

- `GET /data/products` — named data products with owners, classifications, contracts and live probes

- `POST /tasks` — submit a task (async, returns run id)
- `POST /workflows/select` — pick a workflow pattern for a goal `{goal}`

- `POST /admin/spend-authorization/revoke` — revoke a spend authorization `{spend_auth_id}`

- `POST /alerts/watchdog` — run the watchdog and persist alerts
- `POST /geo/places|automata|work-items|routes|manifests` — upsert/plan map records

### Readiness

`/components` reports one of `ready`, `needs_setup`, or `blocked` per
subplatform, with the exact blockers and next commands (it never installs or
executes anything). The dashboard shows the same data and refreshes it every
15 seconds. Readiness understands the shared dependency tree: a component is
"installed" when the root `node_modules` / `.venv` exists, even without a local
copy. It also reports Node engine-range mismatches (the platform standardizes
on Node 24), Bun requirements, missing Qt 6 for CMake/Qt components, and Rust
toolchain/build-output state.

### Submit a task

```json
{
  "task": "Run payment system tests",
  "target": "Pix-Payment-System",
  "command": "pytest -q",
  "cwd": "Pix-Payment-System-main/python",
  "timeout": 120
}
```

Initiative/autorun (planning + execution with live feedback):

```json
{
  "task": "Do trading from 0 funding (no capital)",
  "autorun": true,
  "timeout": 180
}
```

Fields:
- `task` (string) — what to do (used for routing when `target` omitted).
- `target` (string, optional) — subplatform name or component (e.g. `freellmapi`, `Pix-Payment-System`).
- `command` (string, optional) — shell command to execute in the target component (PowerShell on Windows).
- `cwd` (string, optional) — working directory (relative to platform root or absolute within it).
- `timeout` (int, optional) — seconds, default 120.
- `autorun` (bool, optional) — treat task as Primary Initiative/Autorun goal (plan and execute).

Routing: if `target` is set, dispatches there; otherwise keyword-matches task
against subplatform names/descriptions. Initiative/goal tasks are planned and
executed as multi-step workflows. Each dispatch/step is recorded with
status/output; automaton states and reports are persisted under
`orchestrator/state/` (runs, agent states, reports).

### Workflow catalogue and replication

`orchestrator/workflows.py` encodes all 20 agentic LLM workflow patterns, the
five-compartment cascade, the department/admin roles per compartment, the fused
components each stage is built from, and the seven-layer anatomy. The engine is
deterministic and side-effect free: it builds the stage DAG, evaluates each
stage against live readiness (fail-closed), and only then walks the cascade.

```json
{
  "goal": "summarize 400 support tickets from the inbox",
  "workflow": 10,
  "mode": "attest",
  "replicate": true,
  "max_replicas": 5
}
```

- `mode: "plan"` records the DAG and gate decisions.
- `mode: "attest"` also creates and completes a worker per open stage.
- Replication uses the admin's normal `replicate_agent` path; a closed gate or a
  blocked component stops the cascade at that point and the run reports exactly
  which components must be fixed.
- No model calls, shell commands, settlement, or funding happen in this engine.

## Power / capabilities

- Multi-eagent routing and tracked runs (queued/running/completed/failed) with live/streamed step output.
- Automaton states/transitions and mandatory reporting (eagent→admin, admin→operator/audit), exposed via API/UI.
- Primary Initiative/Autorun planning and execution (including 0-funding trading bootstrap workflows).
- Admin responsibilities encoded in planning/execution: erect paywalls, settle, and fund (fail-closed, 0-funding; realized/authorized resources only; Pix-Payment-System African/PIX rails when configured).
- Shell execution within the platform root (build, test, run subplatform tools).
- File/dir operations scoped to the platform root.
- Agentic workflow catalogue (20 patterns) with per-stage gates and a
  fail-closed five-compartment replication cascade (see `workflows/README.md`).
- Musashaban payment & settlement ported to `orchestrator/payment/` — RudiPay
  routers/faucets/transactions/settlements/disputes (fail-closed admin +
  preferred-router-phone gating), funding requests/collections/development
  needs, two-step withdrawal gate, SMS-OTP gate, and the auto-settle-to-cash
  funding state machine. State: `orchestrator/state/payment.db`.
- Sentry department agent (`sentry`, spec + eagent + `agents/specs/sentry.json`,
  registered in `agents/registry.json`): watches deployment, hosting and
  security posture (surfaces, gapinvex hosting facts, protected paths, alerts)
  and reports findings to admin. It never deploys, pays, or changes policy.
- Surfacing surfaces (`orchestrator/surface.py`): probes + status for IPFS
  (`ipfs id`), Cloudflare (`cloudflared`), Tailscale (`tailscale status`).
- Harmony of identities: the TrustWallet address
  `0x61f9FAC0A44e0D975673CB97fc4A615B16398846` is the single trusted wallet
  used everywhere (autoSettleTo, rudi admins, wallets). The other discovered
  chain addresses are not used — ownership was unverifiable, so we fail closed.
- Deep architecture: 6-layer reference stack mapped onto this repo's modules
  (`orchestrator/stack.py`, served at `GET /stack`), the nine-step agent loop,
  protocol/semantic layers, the ten named data products, governance status and
  the four engineering layers every stage runs against (prompt, context,
  harness, loop).
- Fail-closed depth: a gate closes when its independent verifier is blocked,
  a stage with a closed/incomplete depth contract cannot attest, and the
  cascade requires an attestation plus a decided compartment.
- Constitution & soul, bites resolved:
  - **At dispatch** — `dispatch_to_eagent` runs `agent_specs.validate_spec(spec, constitution_sha256(), …)` for every eagent, using `agent_specs.resolve_spec(name)`: the on-disk spec first, then the replica's **carried spec payload** (registry entry in `agent_states`), so replicas can dispatch. A spec that is missing (and not carried), stale (constitution hash mismatch), or structurally invalid blocks the step with a visible error and the shell never runs; valid specs dispatch as before. `GET /agents/validate` + `GET /agents/specs/status` report the whole set; `POST /admin/specs/generate` heals missing specs (canonical `scripts/generate-agents.js --names=<n>` first, Python `agent_specs.build_spec(name)` fallback).
  - **Money movement ("Never harm", "Earn your existence")** — `policy.evaluate` denies financial commands by default. Authorized paths (in order): `authorized_spend`, a live `spend_auth` token (recorded via `admin.authorize_spend`, consumed through `POST /admin/spend-authorization`), `PLATFORM_ALLOW_LIVE_TRADING=1`, or a funding state other than `unfunded`. A wrong-agent or expired token fails closed.
  - **Funding state ("Earn your existence")** — `admin.funding_state()` computes `unfunded` / `float_funded` / `revenue_funded` from the durable funding ledger (`state/funding.jsonl`, written by `admin.record_funding`). In `unfunded`, financial commands stay denied; operator funding records are persisted with evidence and reported to admin.
- Extensible: eagent handlers and richer planning can be added on top of this runtime. Preserves existing dispatch/initiative/streaming behavior.
